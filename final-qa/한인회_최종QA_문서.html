작성 기준: 2026-10-04, 현재 PC의 실제 소스. 프론트 3c52196, 백엔드 63219d7 및 프론트 메인 화면의 기존 미커밋 수정 포함. 실제 신청·승인·사용 사이클은 아직 미검증이다. 이 문서는 소스에서 확인한 절차이며 실행 결과는 BROWSER_QA_REPORT.md와 QA_CASES.md를 함께 확인한다.

1. 접속과 역할

F는 사용자 웹 주소, A는 API·운영 관리자 주소이다. 로컬 기준 F=http://localhost:8088, A=http://localhost:7777. 아래 표의 F/A를 실제 승인된 테스트 주소로 치환한다. 프론트 qa와 production API 설정은 모두 https://koreans.tw다. 이름이 QA라는 이유만으로 테스트 데이터베이스라고 판단하지 않는다. 로컬 관리자 정적 미리보기는 http://localhost:8090/admin/index.html이며 로그인/API/DB 기능은 없다.

1-1. 일반 회원가입→운영자 조회→사용자 첫 진입

2026-10-06 보완. 일반 회원가입은 정회원 신청과 별개다. 기존 TC-AUTH-02는 가입 화면만 확인했고, TC-AUTH-06의 실제 가입은 미실행이다. 아래 절차는 소스 기준이며 상세 검증은 TC-SIGNUP-01~07을 따른다.

  1. 비로그인 상태에서 F/login의 회원가입으로 F/register에 들어간다. 신규 QA 아이디·비밀번호·닉네임·승인된 수신함 이메일을 입력한다. 현재 프론트는 아이디와 비밀번호 각각 4자리 이상을 확인한다. 최종 허용 규칙은 서버 검증도 함께 확인한다.
  2. 이용약관·개인정보 취급방침 링크를 확인하고 동의한다. 미동의·필수값 누락·잘못된 이메일 형식에서는 가입/인증이 진행되지 않아야 한다.
  3. 이메일 인증번호 발송→QA 수신함 확인→인증번호 검증 순서로 진행한다. 잘못된 코드, 재발송 전 코드, 이미 사용한 코드도 별도 확인한다. 인증번호·실제 이메일은 결과 파일이나 캡처에 기록하지 않는다.
  4. 가입 버튼을 누른다. 정상 가입 뒤 자동 로그인을 시도하며, 자동 로그인 실패 시 가입 완료 안내와 로그인 화면으로 이동하는 분기가 있다. 자동 로그인 실패만으로 가입 자체가 실패했다고 판단해 다시 제출하지 않는다.
  5. 운영자는 A/admin/index.html?section=users에서 신규 QA 회원을 찾아 회원 ID·닉네임·일반회원 ROLE_USER를 확인한다. 사용자 F/main·F/mypage의 정보와 같은 계정인지 비교한다. 가입만으로 ROLE_REGULAR/ROLE_PARTNER/ROLE_ADMIN 권한이 생기면 안 된다.
  6. 로그아웃→F/login에서 방금 만든 계정으로 재로그인→F/mypage 재조회한다. 신규 회원은 F/membership에서 정회원/제휴업체 신청 사이클을 이어간다. 일반 회원가입 자체에는 멤버십 승인 절차를 섞지 않는다.
  7. 동일 아이디·동일 이메일 재가입을 각각 시도해 중복 안내와 회원 수 미증가를 확인한다. 인증 전 제출, 이메일 변경 후 제출, 인증 재사용은 새 테스트 데이터로 확인한다.

연결 API: POST /api/auth/sendSignupAuthCode → /api/auth/verifySignupAuthCode → /api/auth/register → /api/auth/login. 서버는 인증 완료 이메일과 아이디·이메일 중복을 확인하며, 일반 가입 UI는 역할을 전송하지 않아 기본 ROLE_USER 분기를 사용한다. 인증 유효시간은 현재 확인한 AuthController의 메모리 저장/검증 코드에서 TTL 처리가 보이지 않으므로 만료 정책과 실제 차단을 추가 확인한다. “만료 안내 문구가 있다”는 사실만으로 만료 검증 완료로 판정하지 않는다.

현재 회원가입 화면 증빙은 7절의 캡처를 참고한다. 이메일 인증 성공·가입 완료·운영자 조회·첫 메인·재로그인 캡처는 실제 실행 후 추가한다.

1-2. 소셜 회원가입 검증: Google·카카오·네이버

F/register에는 네이버·카카오·Google 가입 버튼이 있다. F/login의 소셜 로그인과 구분하여, 제공자별로 아직 이 서비스에 가입하지 않은 QA 계정을 준비한다. 상세 검증은 TC-SOCIAL-01~09를 따른다.

GoogleF/register→약관 동의→Google 인증→POST /api/social/register신규 회원 1명, ROLE_USER, 자동 로그인·F/mypage, 운영자 users 조회

네이버F/register→약관 동의→네이버 인증→POST /api/social/naver/register웹 code/state와 네이티브 사용자정보 분기를 나눠 같은 회원·권한 확인
  1. 제공자별 신규 계정으로 약관 미동의 시도→동의 후 인증→콜백 복귀→가입 완료→F/main·F/mypage→운영자 회원 조회까지 한 사이클로 확인한다. 소셜 인증창이 열리거나 콜백이 돌아오는 것만으로 PASS를 주지 않는다.
  2. 같은 소셜 계정으로 F/register에서 다시 가입하면 현재 서버는 중복 username/email에 409와 로그인 이용 안내를 반환한다. 회원이 추가되지 않았는지 확인한 뒤 F/login의 같은 제공자로 재로그인하여 기존 회원 ID가 유지되는지 확인한다.
  3. 기존 일반회원 또는 다른 제공자와 이메일이 같은 경우도 확인한다. 현재 가입 서버는 이메일 중복을 거절한다. 자동 계정 합치기를 기대값으로 두지 않으며, 계정 연결 정책은 담당자 확인 사항으로 남긴다.
  4. 인증창 닫기·사용자 취소·동의 거절·팝업 차단·통신 실패 시 가입 화면으로 복귀하고 회원/로그인 상태가 잘못 생성되지 않아야 한다. 이후 다시 시도할 수 있는지도 확인한다.
  5. 이메일 미제공·닉네임 누락 시 오류 또는 대체 프로필 처리와 운영자 조회를 확인한다. 소스에는 임시 이메일 생성 분기가 있으므로 “제공자 이메일 인증 완료”로 기록하지 않는다. 프로필 이미지 연동도 현재 서버가 null을 지정하는 분기가 있어 별도 정책 확인이 필요하다.
  6. 웹과 실제 출시 iOS/Android에서 지원 여부·승인된 redirect/callback 주소를 각각 확인한다. 한 플랫폼의 성공을 다른 플랫폼 PASS로 재사용하지 않는다. OAuth code/state·토큰·제공자 계정정보는 증빙에 저장하지 않는다.

추가 확인: 소셜 프로필과 로그인 세션 응답의 ID 매핑, 이메일 중복 정책, 인증 취소 후 잔여 세션, 출시 플랫폼별 콜백 설정, 가입 후 일반회원 권한 유지. 현재 소셜 신규 가입·재로그인·실기기 검증은 미실행/BLOCKED다.

2. 메인 화면 운영: 설정부터 노출까지

  1. 운영자 로그인 후 메인 화면 메뉴에서 TOP 배너 또는 Middle 아이콘 탭을 선택한다.
  2. 제목, 설명, 이동 링크, 순서(1 이상), 이미지, 활성 여부를 입력한다. TOP에는 버튼 텍스트도 필요하다.
  3. 이미지 업로드와 저장을 구분한다. 업로드 미리보기가 보이더라도 목록 저장 완료와 재조회까지 확인한다.
  4. TOP 활성 항목은 최대 5개, 중앙 아이콘은 최대 6개다. 비활성 항목을 준비해 활성 상한을 넘기는 테스트를 별도 수행한다.
  5. 사용자 F/main을 새로 열어 제목·설명·이미지·순서·버튼을 확인한다. 해당 링크를 눌러 내부 화면 또는 외부 주소 이동을 확인한다.
  6. 수정 후 다시 사용자 메인을 열어 변경값을 확인한다. 활성 해제·삭제 후에는 사용자 목록에서 사라져야 한다.

사용자 공개 조회는 /api/v2/main/top-banners, /middle-icons다. 활성·미삭제 항목을 순서 오름차순, 같은 순서에서는 생성일 내림차순으로 읽는다. 메인 컴포넌트는 진입 시 데이터를 가져오므로 관리 저장 후 사용자 화면을 재진입/새로고침하여 확인한다. API 장애와 콘텐츠 0개를 정상 노출로 판정하지 않는다.

3. 정회원 신청→운영자 승인→사용자 확인

  1. 일반 테스트 회원으로 F/membership에 들어가 정회원을 선택한다.
  2. 신청 사유·연락처·필수 입력과 증빙 파일을 채우고 신청한다. 실제 개인정보 대신 QA용 자료를 사용한다.
  3. 사용자 화면에서 승인 대기를 확인한다. 운영자는 membership 메뉴의 유형 REGULAR과 대기 상태로 같은 신청을 찾는다.
  4. 상세 정보와 첨부를 확인하고 승인(apply) 또는 반려(reject)와 사유를 저장한다.
  5. 사용자는 F/membership을 다시 조회해 승인/반려와 사유를 확인한다. 역할을 최신화하기 위해 로그아웃 후 다시 로그인하고 F/mypage 등급을 확인한다.
  6. 승인 후에는 정회원 쿠폰을 받기/사용할 수 있어야 한다. 반려 후에는 신청 수정·재신청을 확인한다.
저장 상태의미소스에서 확인한 권한 처리

승인 이력이 있는 사용자를 반려로 바꾸는 것과 취소하는 것은 현재 권한 처리 방식이 다르다. 실제 등급 회수 정책을 확인한 뒤 처리한다. 사용자 화면은 cancel을 별도 표시하지 않아 “미신청”으로 나타날 수 있다. 승인 완료된 신청은 사용자 수정이 차단된다.

4. 제휴업체 신청→승인→업체 등록

  1. F/membership에서 제휴업체 PARTNER 유형을 선택해 회사명·신청인·연락처·자료를 입력하고 신청한다.
  2. 운영자는 membership에서 PARTNER 신청을 찾아 승인하고 사용자는 재로그인하여 제휴 권한을 확인한다.
  3. F/store(한인맵)의 + 버튼을 눌러 제휴업체 등록 모달을 연다. 해당 버튼은 현재 ROLE_PARTNER에 표시된다.
  4. 업체명, 검색해서 선택한 주소/좌표, 카테고리를 입력하고 등록한다. 현재 연결은 components/store/index.js → src/hooks/useMap.js → src/api/placeApi.js → POST /api/v2/places다.
  5. 등록 성공 후 지도/목록이 갱신되는지 확인하고 F/store/manage에서 본인 업체가 보이는지 확인한다.
  6. 일반 사용자로 검색하여 같은 업체의 이름·주소·카테고리·제휴 표시·마커·상세를 확인한다. F/main 추천 업체에도 노출되는지 확인하되, 메인은 첫 페이지 5개만 조회하므로 항상 고정 노출된다고 가정하지 않는다.
  7. 업체 수정 후 사용자 화면을 재조회한다. 다른 업체 계정은 이 업체를 수정/삭제하지 못해야 한다.

현재 운영자 업체 승인 단계는 별도 구현된 것으로 확인되지 않았다. 회원의 제휴 권한 승인과 업체 데이터 등록을 분리해 확인한다. 업체 isPartner 표시값과 회원 ROLE_PARTNER를 같은 상태로 가정하지 않는다.

5. 쿠폰 등록→사용자 받기→매장 사용 완료

  1. 제휴업체가 F/coupon/manage/create에서 본인 업체를 연결하고 제목·설명·코드·만료일·쿠폰 유형·직원 확인 비밀번호를 입력한다.
  2. UNIVERSAL(일반), LIMITED(선착순), PERSONAL(지정 대상)을 구분한다. LIMITED는 사용 상한을, PERSONAL은 대상 테스트 회원을 지정한다.
  3. 제휴업체 관리 목록과 운영자 coupons 메뉴에서 같은 쿠폰을 확인한다.
  4. 승인된 정회원이 F/coupon에서 같은 쿠폰을 열고 받기를 누른다. F/coupon/my 또는 F/mypage의 쿠폰 목록에 미사용으로 보이는지 확인한다.
  5. 매장에서 해당 쿠폰 상세/마이페이지 사용 창을 열고 직원 확인 비밀번호를 입력해 사용한다. PIN은 스크린샷에 남기지 않는다.
  6. UI는 POST /api/v2/coupon/use에 코드와 비밀번호를 전송한다. 성공 후 내 쿠폰은 사용완료, 사용일시는 저장되고 운영자 발급 내역에도 같은 사용자 쿠폰의 사용일이 보여야 한다.
  7. 재사용과 잘못된 PIN은 실패하고 상태·사용 수량이 바뀌지 않아야 한다. 새로고침과 재로그인 후에도 사용완료를 유지해야 한다.

LIMITED 수량은 받기 시 증가하지 않고 사용 완료 시 증가한다. 미발급, 만료, 숨김, 이미 사용한 쿠폰은 사용이 차단된다. PERSONAL은 지정 명단과 발급 매핑을 함께 확인한다. 일반회원 ROLE_USER는 받기·사용 API 허용 역할에 포함되지 않는다.

주의: 메인 화면 “내 쿠폰” 영역은 현재 개인 보관함 API가 아닌 전체 /api/v2/coupon/list?status=ALL을 호출한다. 실제 내 쿠폰함과 내용·사용 상태가 일치하는지는 최종 QA에서 반드시 확인해야 한다.

한 TC 수행 방식

TC를 RUNNING으로 표시 → 전제/이전 상태 기록 → 해당 역할의 UI로 행동 → method/path/status만 기록 → 같은 데이터 재조회 → 반대 역할 UI에서 확인 → 새로고침 후 유지 확인 → 기대값 비교 → PASS/FAIL/BLOCKED와 증빙 저장.

PASS는 해당 TC의 모든 기대 결과와 사후 상태가 관찰된 경우다. 소스에서 로직을 발견한 것, 빈 HTTP 200, 토스트, 정적 양식만으로 PASS를 만들지 않는다. API 직접 호출은 보조 검증이며 UI 동선의 성공을 대신하지 않는다.

실행상태: NOT_RUN, RUNNING, PASS, FAIL, BLOCKED. SOURCE_CONFIRMED는 소스 분석 수준이며 실행상태와 별도 필드다. 네트워크/계정 장애는 BLOCKED, 기대와 다르게 관찰된 제품 동작은 FAIL. SKIPPED를 PASS로 합산하지 않는다.

가입 중단 시 provider 별칭, 플랫폼, 회원 생성 여부, 마지막 완료 단계(코드 발송/인증/가입/자동 로그인/운영 조회), 다음 행동을 저장한다. 회원 생성 후 자동 로그인 실패는 회원 조회 후 수동 로그인부터 재개한다. 가입 화면 PASS와 신규 회원 생성 PASS는 별도다. AUTH-06/08과 상세 SIGNUP/SOCIAL은 같은 실행 증빙을 연결하여 중복 가입하지 않는다. 인증 TTL·계정 연결·프로필 대체값 정책이 미확정이면 해당 정책 검증은 BLOCKED로 유지한다.
