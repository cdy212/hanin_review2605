# AI 최종 QA 지침·워크플로우

## 목표와 진입 순서

운영자 설정·승인부터 사용자 노출·사용까지 기능 단위로 끝까지 검증한다. 결과는 운영자 매뉴얼, QA_CASES.md, 실행 증빙, 00_progress.md에 함께 반영한다.

1. 00_progress.md → E2E_RETEST_GUIDE.md → QA_CASES.md → FINDINGS.md를 읽는다.
2. 양쪽 저장소 AGENTS.md, 프론트 docs/프로젝트가이드문서.md, 백엔드 AGENT2.md 및 LOCAL_TEST_GUIDE.md를 따른다.
3. 현재 commit, git status, 포트, 실제 API 목적지를 확인한다. 과거 문서의 환경·계정 성공을 현재 성공으로 간주하지 않는다.
4. `SOURCE_MAP.md`, `source_inventory.json`에서 화면→API 근거를 확인한다. 소스가 바뀌면 연결표와 영향 TC를 갱신한다.
5. 다음 미완료 TC를 실행하고 마지막 완료 단계·증빙 파일·다음 행동을 즉시 저장한다.

## 테스트 환경과 데이터

- 사용자 요청은 QA 사이클과 문서 작성이다. 테스트 전 운영/QA 구분 및 역할별 계정을 확정한다. qa 변형은 koreans.tw이므로 자동으로 안전한 환경이라 판단하지 않는다.
- application*.properties, Firebase·소셜·secret·credential·key 설정 파일은 읽거나 수정하지 않는다.
- 현재 mockAuthSession 또는 임의 localStorage 토큰을 실제 인증 성공 증거로 사용하지 않는다.
- 역할별 독립 브라우저 세션을 사용한다. U=일반, R=정회원, P1/P2=서로 다른 제휴업체, O=운영자. 신청→승인 검증에는 별도 신규 일반 계정을 사용한다.
- 가입 검증은 일반 신규 수신함과 Google·카카오·네이버별 미가입 QA 계정을 따로 준비한다. 가입 후 회원 ID와 제공자 별칭만 기록하고 실제 이메일·OAuth code/state·인증번호는 저장하지 않는다. 같은 이메일 충돌 검증은 별도 계정으로 분리한다.
- runId는 `QA_YYYYMMDD_HHMM`으로 하고 모든 생성 제목·업체명에 붙인다. record ID와 역할 별칭만 기록한다.
- 기존 운영 데이터의 활성·권한·노출을 변경하지 않는다. 이번 runId 데이터의 변경과 종료 정리만 수행한다. 쿠폰 사용 이력은 단순 재시도로 되돌릴 수 없으므로 새 데이터로 분리한다.
- 이메일·푸시는 승인된 수신함/실기기 한 곳으로만 보낸다. 일괄 발송·대량 내보내기·탈퇴는 별도 대상 확인 후 수행한다.

| W2 | TC 준비·baseline·테스트 데이터 | QA_CASES.md와 run 기록 |

| W3-A | 메인 CMS→일반 메인 | 이미지·텍스트·순서·링크·비활성 반영 |
| W3-B | REGULAR/PARTNER 신청→운영 심사→재로그인 | 신청 ID·상태·권한·화면 차이 |
| W3-C | 제휴 업체 등록→사용자 지도/메인→수정 | place ID·소유자·검색·마커 |

## 한 TC 수행 방식

TC를 RUNNING으로 표시 → 전제/이전 상태 기록 → 해당 역할의 UI로 행동 → method/path/status만 기록 → 같은 데이터 재조회 → 반대 역할 UI에서 확인 → 새로고침 후 유지 확인 → 기대값 비교 → PASS/FAIL/BLOCKED와 증빙 저장.

PASS는 해당 TC의 모든 기대 결과와 사후 상태가 관찰된 경우다. 소스에서 로직을 발견한 것, 빈 HTTP 200, 토스트, 정적 양식만으로 PASS를 만들지 않는다. API 직접 호출은 보조 검증이며 UI 동선의 성공을 대신하지 않는다.

실행상태: NOT_RUN, RUNNING, PASS, FAIL, BLOCKED. SOURCE_CONFIRMED는 소스 분석 수준이며 실행상태와 별도 필드다. 네트워크/계정 장애는 BLOCKED, 기대와 다르게 관찰된 제품 동작은 FAIL. SKIPPED를 PASS로 합산하지 않는다.

## 진행 기록과 중단·재개

`runs/{runId}.json` 또는 동일 형식 Markdown에 아래를 남긴다.

```json
{
  "runId": "QA_YYYYMMDD_HHMM",
  "environment": {"frontend": "확인한 주소", "backend": "확인한 주소", "dataTargetConfirmed": false},
  "source": {"frontendCommit": "commit", "backendCommit": "commit", "dirtyPaths": []},
  "currentCase": "TC-MAIN-01",
  "status": "BLOCKED",
  "lastCompletedStep": "운영자 로그인 화면 렌더",
  "recordIds": {},
  "evidence": [],
  "reason": "실제 테스트 환경 및 역할별 계정 미확정",
  "nextAction": "대상 확정 후 운영자 로그인하고 CMS baseline 기록"
}
```

부작용 직후 기록이 없으면 재시작할 때 POST부터 다시 보내지 않는다. 먼저 동일 runId의 목록/신청/발급 상태를 조회해 실행 여부를 확인한다. 이미 사용한 쿠폰을 새 쿠폰처럼 처리하지 않는다. 실패 전 상태와 실패 후 상태를 구분한다.

가입 중단 시 provider 별칭, 플랫폼, 회원 생성 여부, 마지막 완료 단계(코드 발송/인증/가입/자동 로그인/운영 조회), 다음 행동을 저장한다. 회원 생성 후 자동 로그인 실패는 회원 조회 후 수동 로그인부터 재개한다. 가입 화면 PASS와 신규 회원 생성 PASS는 별도다. AUTH-06/08과 상세 SIGNUP/SOCIAL은 같은 실행 증빙을 연결하여 중복 가입하지 않는다. 인증 TTL·계정 연결·프로필 대체값 정책이 미확정이면 해당 정책 검증은 BLOCKED로 유지한다.

사용량 제한 또는 컨텍스트 압축 전 00_progress.md에 마지막 TC, 마지막 완료 단계, 생성 ID, 미완료 행동, 서버 실행 상태를 기록한다. 제한 초기화 후 최신 파일부터 재개한다. 리셋 크레딧 사용·구매는 하지 않는다. 자동화 `qa`는 이 채팅에 매시간 확인하도록 등록되었다. 현재 제한 초기화 시각은 한도 창의 리셋 시각이며 컨텍스트가 만료되는 확정 시각이 아니다. 예약 실행은 앱/호스트가 실행 가능한 상태인지 확인하고 실제 동작을 검증한다.

작업 시작 시 확인한 계정 사용량은 5시간 창 1%, 주간 창 0%였다. 해당 5시간 창 초기화 시각은 2026-10-05 02:38:44 KST이며 이후 사용량/창은 다시 조회해야 한다. 자동화는 한도 우회 기능이 아니라 실행 가능한 시점에 기록을 읽고 이어가는 후속 작업이다.

## 브라우저·캡처

- CUA 또는 준비된 프로젝트 브라우저 자동화 도구로 실제 화면을 읽고 명확한 locator를 선택한다. CUA의 현재 API 문서를 먼저 읽는다.
- 사용자와 운영자 세션을 혼용하지 않는다. URL의 role와 저장된 권한을 구분한다.
- 캡처 파일: screenshots/{runId}_{tcId}_{step}.jpg/png. 인증 입력·PIN·토큰·개인정보가 없는 상태에서 촬영한다.
- 로그인 화면, CMS 저장·목록, 사용자 메인, 신청 대기·승인, 업체 목록·상세, 쿠폰 발급·사용완료를 각각 남긴다.
- 정적 8090 템플릿에는 “소스 미리보기 / API·DB 미연동”을 적는다. UI에 가짜 성공 상태를 주입해 캡처하지 않는다.
- 실패는 주소·관찰 메시지·원인 후보·재현 순서를 남긴다. 네트워크 본문과 Authorization을 통째로 저장하지 않는다.

## 최종 출력

운영자 매뉴얼은 실행 방법 중심, QA 리포트는 Expected/Actual/판정 중심, FINDINGS는 확인 근거와 다음 검증 중심으로 작성한다. 기존 분석 문서와 중복한 새 개발 가이드를 만들지 않는다. 코드 수정·커밋·배포는 이 문서 작성 범위와 분리한다. 모든 사이클 검증이 끝나면 자동화를 중지한다.
